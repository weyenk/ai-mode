## ux review

### Blocking
- The CLI surface is not complete enough to be production-ready. The help text and output order are specified, but the exact shape of the Story Contract and layer plan in stdout are not defined enough for a human to scan, compare, or validate without reading the full JSON artifact.
- The command has no visible state persistence model. A human cannot see whether a run is paused, whether `--resume` continues from the contract or the decision log, or whether the current round is lost after a crash.
- The verdict and layer plan are not clearly separated. In the current spec, the first line is the verdict, then the layer plan, then the contract, but that structure is not enforced in the CLI output spec. A human reading the command output will scan for the verdict first, then the plan, then the contract, but the spec does not confirm that order.
- The uncertainty and parked-question flow is not visible enough. The state transitions `open -> parked -> re-asked -> resolved | escalated` are described, but there is no indication of whether a parked question is shown in the contract, whether it blocks the verdict, or whether it is highlighted in the summary.
- The audit levels are not differentiated enough. `summary` and `full` write different amounts of data, but the spec does not explain what a human should expect to see at a glance. That makes it hard to choose the right audit level before running.
- The exit codes are not sufficient for scripting. Only `0`, `1`, `2`, `3` are defined, but there is no explanation of what each code means in plain English or whether the command writes a human-readable error message alongside the code.

### Non-blocking
- The CLI command is mostly clear in concept. The inputs, flags, and output are specified enough for a small team to implement, but not enough for a public or enterprise-grade tool.
- The layer plan is logically sound. The dependency order, test levels, and gate states are well-defined, and the stack design aligns with GitHub’s guidance.
- The state directory structure is reasonable. `contract.json`, `decisions.jsonl`, `parked.jsonl`, and `transcript.jsonl` are a standard pattern for this kind of session.
- The security model is solid. Data delimiters, secrets, caller allowlists, and audit file modes are well-defined and appropriate for a production system.

### Proposed edits
- Define the exact CLI output order. The command should print:
  1. verdict line
  2. layer plan
  3. Story Contract
  4. open/parked/escalated questions
- Add a visible state summary to the CLI output. For example:
  ```
  Meeting ID: abcdef-1234
  Current round: 2 of 3
  Next role: architect
  Status: paused
  ```
- Make the verdict and layer plan more distinct. The verdict should be the first line, with a clear status code and short summary. The layer plan should be a structured table or JSON block with minimal formatting.
- Clarify the parked-question flow. If a question is parked, it should be shown in the contract with a status field and a reason. If it is escalated, it should be shown in the summary and not hidden behind JSON.
- Define the audit levels more clearly. For example:
  - `summary`: verdict, layer plan, contract, questions
  - `full`: verdict, layer plan, contract, questions, prompt/response log
- Add scripting-friendly error messages. Each exit code should have a plain-English explanation printed to stderr, not just a numeric code.
- Define the state persistence model. The command should write its own state files, not depend on external tools like `gh-stack` for session persistence. The state dir should be owned by the command and persisted on exit.
- Add a visible round counter. The current round and next role should be shown in the CLI output and in the state files.
- Add a visible caller identity. The calling skill or human should be shown in the CLI output and in the state files.
- Add a visible verdict justification. If the verdict is `not-ready` or `paused`, the reason should be shown in the CLI output and in the contract.
- Add a visible test assignment model. Each scenario should be assigned to exactly one layer, and the test level should be shown in the layer plan or contract.
- Add a visible gate state model. Each gate should be shown with its current state and whether it is available or not available.
- Add a visible approval model. The command should not proceed after a `ready` verdict unless the human has approved the Story Contract. That should be shown in the CLI output and in the state files.
- Add a visible resume model. The `--resume` command should continue from the current round and the current role, not from the first round.
- Add a visible input precedence model. The positional string, `--story -`, `--story FILE`, and JSON contract should be clearly ordered and documented in the help text.
- Add a visible security model. The command should scan for tokens and secrets before any model call, and write a redaction log if `--audit full` is used.
- Add a visible caller allowlist model. The command should validate the caller ID against a static allowlist before any model call, and reject unknown callers with a clear error message.
- Add a visible repo path model. The command should validate the repo path against a trusted roots allowlist before any model call, and reject remote or malformed paths with a clear error message.
- Add a visible token handling model. Board/API tokens should not appear in the artifacts or the repo; they should be stored in the OS keychain or a fallback file with mode 0600.
- Add a visible log format model. The command should use a consistent log format with a clear timestamp, role, decision, rationale, and trace/span.
- Add a visible schema model. The command should validate all inputs against a strict JSON schema before any model call, and reject malformed contracts with a clear error message.
- Add a visible trace/span model. The command should include trace/span information in the state files and the JSON artifact, and not rely on external tools for tracing.
- Add a visible performance model. The command should not include performance or AI eval layers unless they are available and configured.
- Add a visible dynamic-security model. The command should only run the dynamic-security gate on exposed surfaces, and not on internal or private endpoints.
- Add a visible CI gate model. The command should not include CI gates unless they are available and configured.
- Add a visible review flow model. The command should not submit or merge PRs without human approval. That is not part of the CLI surface, but it should be clear in the spec.
- Add a visible handoff model. The command should not hand off to the coder until the architect has completed the layer plan and the human has approved the Story Contract.
- Add a visible escalation model. The command should not escalate a parked question until all other questions are resolved.
- Add a visible re-run model. The command should not re-run a failed layer until the current layer is fixed.
- Add a visible merge model. The command should not merge a stack until the bottom layer is approved and green.
- Add a visible review order model. The command should not request reviews in parallel unless the layers are independent and the review order is clear.
- Add a visible fix model. The command should not fix a defect in the Story Contract without reopening the base layer and restacking the entire stack.
