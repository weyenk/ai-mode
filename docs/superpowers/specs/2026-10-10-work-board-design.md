# Work board and companion services — design notes

Status: **draft, split out of the Three Amigos spec** (`2026-10-10-three-amigos-design.md`) after round-2 product review. Pipeline-level; not specific to `ai-mode amigos`. Captures the board decision, trial results, and the companion-service idea.

## Board decision and trial results (2026-10-10)

Work is tracked on a **Vikunja** board (single Go binary, SQLite by default, web UI). Epics are the idea-origination point; amigos runs per story mid-funnel. `provenance.caller_id` may carry a Vikunja task id; a verdict maps to a bucket/column move (`ready` forward, `not-ready` stays with notes, `paused` to a needs-human bucket).

**Why not Kan:** trialled v0.20.1 (2026-10-10). The CLI was fine (`--json`, `-I`, parent links by card id), but concurrent writers corrupted the board (column membership lives in one `config.toml`; 9 of 20 parallel adds orphaned), `kan serve` has no host flag and binds all interfaces, there is no auth, and CORS is `*` with write methods. Fixing it meant maintaining a fork.

**Vikunja findings (official docs, vikunja.io/docs/config-options and /docs/veans):** `service.interface` (env `VIKUNJA_SERVICE_INTERFACE`) defaults to `:3456`, all interfaces, so ai-mode must set `127.0.0.1:<port>`; `service.unixsocket` is an alternative; `service.secret` defaults to a random per-start value, so pin it. Vikunja ships **veans**, an experimental agent CLI (needs Vikunja 2.4.0+): JSON output; `init` signs in once via OAuth, creates a **bot user** and mints a long-lived scoped API token stored in the OS keychain (or `VEANS_TOKEN`); commands `list/show/create/update/claim/api`; `create` supports `--parent` and `--blocked-by`; statuses map to five fixed buckets (Todo, In Progress, In Review, Done, Scrapped); the agent never moves work to Done, a human does. This answers the open questions on API tokens, relations and bucket moves.

**Decision: API the whole way (v2), no veans, no webhooks for now.** Build a thin stdlib Go client against `/api/v2` (OpenAPI 3.1 spec served at `/api/v2/openapi.json`; Vikunja 2.4.0+). v2 gives `PATCH` merge updates, RFC 9457 errors, and `ETag`/`If-Match` preconditions (use for optimistic concurrency instead of a lock wrapper; still to be tested under 20 parallel writers). veans is dropped (fixed five-stage model, one bot per repo). Webhooks (board -> pipeline trigger) deferred: loopback delivery is blocked by default, there are no retries, and they need a listener; if added later, pair with reconcile polling and treat payloads as data.

**Identity: one bot user per agent/skill** (docs: vikunja.io/docs/bot-users). Bots are normal accounts with `bot-` usernames, no password/email (API token only), owned by a human (deleted with the owner), marked with a badge in the UI, shareable into projects, assignable, mentionable. Each bot gets its own scoped API token (`tk_` prefix), so the board shows which agent made each change and the board enforces the skill allowlist: a bot only reaches projects shared with it and only does what its token scope permits. Labels are shared between an owner and their bots (a bot edits only labels it created). Proposed bots: `bot-chief`, `bot-amigos`, `bot-product`, `bot-qa`, `bot-architect`, `bot-coder`. Creating bots is documented in the UI (Settings -> Bots); veans does it via the API, so the endpoint exists but is not documented on these pages (verify in the OpenAPI spec). Tokens live in the OS keychain or a 0600 file, never in the repo or transcripts (feeds the audit redaction pass).

**Trial results (Vikunja v2.7.0, macOS arm64 binary from the official GitHub release, scratch dir, loopback `127.0.0.1:3460`, SQLite, 2026-10-10):**
- Works: bot users via `POST /user/bots`; per-bot scoped tokens via `POST /tokens` with `owner_id` and a `permissions` map of route-group -> actions (tasks, tasks_comments, tasks_relations, projects, projects_views...). Attribution is correct: `created_by` and comment `author` show the bot. Scope enforcement is real: a bot with no delete scope got 401 on deleting tasks/projects, creating bots, and minting tokens; bots only see projects shared with them. Custom kanban buckets (idea ... needs-human) via `POST /projects/{p}/views/{v}/buckets`; moves via **`PUT`** `/projects/{p}/views/{v}/buckets/{b}/tasks` `{task_id}`; relations via `POST /tasks/{id}/relations` (`subtask`, `parenttask`, `blocking`, ...); `GET /api/v2/openapi.json` (136 paths); route list also has an `mcp` group (unexplored). Bind confirmed `127.0.0.1`.
- **Problem 1: concurrent writes fail on SQLite.** `database is locked` -> HTTP 500. Even 2 concurrent writers failed ~75% of creates; 20-40 parallel creates/moves/relations mostly failed. No SQLite busy-timeout option is documented (`maxopenconnections` applies only to MySQL/Postgres). Behind a **single-writer gate** (one write in flight) 40 creates, 40 moves and 20 relations were 100% clean and the board state was consistent. Requirement: the ai-mode client serializes all writes (in-process mutex plus an inter-process lock), or run Postgres. A solo 500 early in the trial was probably the same issue.
- **Problem 2: `If-Match` is not enforced on task `PATCH`/`PUT`** (stale and bogus `If-Match` values were accepted and overwrote newer data), despite the v2 docs. `ETag` and `If-None-Match` (304) work for reads, but ETags are second-granular. Do not rely on optimistic concurrency; use the write gate and read-modify-write discipline, or retest on a later release.
- **Postgres fixes concurrency (2026-10-10).** Same Vikunja v2.7.0 binary against `postgres:17` run with Apple's `container` CLI 1.5.0 (one lightweight arm64 VM, ~370 MiB used of its 1 GiB, published to `127.0.0.1:5433` only). Zero errors, no write gate: 40 creates/20 workers (p50 83 ms, 0.24 s total), 40 moves, 20 moves of the same task (task ended in exactly one bucket), 20 parallel relations (all 20 recorded), 60 creates at 2/8/32 workers (all 201), 30 writes mixed with 60 reads (all OK). Vikunja itself ~100 MB RSS. `If-Match` is still not enforced (it is application-level, not a database matter). **Decision input:** Postgres for the board in production; SQLite acceptable only with a single-writer gate in the client.
- Minor: failed auth is `401` (not 403); `PATCH` with an unchanged value returns `304`; a Pro license is not needed for any of this.
- Still unverified: Postgres under the same load; whether `mcp` routes are usable; webhooks to loopback (blocked by default).

Companion web services (the board for dev-shop, ComfyUI for av-club, a notebook/podcast tool for learning-center) imply a generic per-profile service concept in `ai-mode` (declare command, port, health check, loopback guard; started by `use`, stopped on profile switch, checked by `doctor`). To be specced separately.
